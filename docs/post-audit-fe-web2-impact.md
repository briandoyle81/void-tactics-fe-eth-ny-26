## Web2 Backend: All Clear

The web2 game mode reimplements combat/movement server-side in TypeScript (`app/lib/gameEngineWeb2.ts`, `prisma/schema.prisma`, `app/api/games/[id]/*`) so wallet-less players can play the same game. Checked all 5 bug classes the audit found and fixed on-chain — none are present here, and none are downstream of the contract fix (this code never shared logic with the Solidity in the first place, so a contract-side fix has no bearing on it either way):

**W-1 — Negative-coordinate "teleport" (audit H-02/M-06).** The Solidity bug was an upper-bound-only grid check that let a ship move to a negative row/col and hide off-grid. Web2 movement validation (`gameEngineWeb2.ts`, `validateDestinationAndTarget`) doesn't check raw coordinates at all — it requires the destination to appear in a candidate list generated by `computeMovementRange` (`app/utils/gameGridRangesWeb2.ts`), which clamps candidates to `[0, dim-1]` structurally before they're ever offered. A negative coordinate simply can't match any candidate and the move is rejected. **No bug, no fix needed.**

**W-2 — Flak damage mutation across targets (audit H-03).** The Solidity bug reused a `flakStrength` variable as an accumulator, so each subsequent target in a loop got progressively less damage. Web2's flak resolution recomputes `baseDamage` fresh from `attackerAttrs.gunDamage` for every target (`applyShootDamage` in `gameEngineWeb2.ts`) — nothing is written back to a shared base value between iterations. **No bug, no fix needed.**

**W-3 — Repair-drone overflow (audit M-02).** The Solidity bug was a `uint8` addition that could overflow/revert before the max-HP cap was checked. Web2 uses `Math.min(maxHullPoints, hullPoints + healAmount)` (`gameEngineWeb2.ts`) — JS numbers don't wrap at 8 bits, and the clamp is applied correctly regardless of operand size or order. **No bug, no fix needed.**

**W-4 — Draw/"ended" ambiguity (audit L-04).** The Solidity bug was that `winner == address(0)` meant both "still in progress" and "ended in a draw," letting `flee`/`moveShip` keep operating on a finished draw. Web2 already has an explicit `GamePhase` enum (`ACTIVE`/`COMPLETED`/`TIMED_OUT`/`ABANDONED` — `prisma/schema.prisma`) independent of any winner field, and a draw sets a real sentinel `WEB2_TIE_SENTINEL` rather than leaving `winnerId` ambiguous. Every guard (`moveShip`, `flee`, `timeout` routes) checks `phase !== ACTIVE`, never a winner-null check. **No bug, no fix needed** — web2 was never exposed to the ambiguity the Solidity fix addresses, because it modeled game state differently from the start.

**W-5 — Timeout winner-determination (audit M-07 — confirmed not-a-bug on-chain, but worth checking the web2 equivalent for the same property).** Solidity's guard prevents the player whose turn timed out from calling the function to award themselves the win. Web2's timeout route (`app/api/games/[id]/timeout/route.ts`) derives the winner structurally from `game.currentTurn` — `winnerId = currentTurn === player1Id ? player2Id : player1Id` — independent of which authenticated user calls the endpoint. Functionally equivalent protection (arguably stronger, since it doesn't rely on a `msg.sender` check at all). **No bug, no fix needed.**

## Frontend Findings

### A — `TIE_ADDRESS` dead sentinel in `Games.tsx` / `GameDisplay.tsx` — **[Actionable now]**

**Files:** `app/components/Games.tsx:17-18,50-51,255-258`, `app/components/GameDisplay.tsx` (same zero-address assumption)

```ts
const ZERO_ADDRESS = "0x0000000000000000000000000000000000000000";
const TIE_ADDRESS = "0x0000000000000000000000000000000000000001";
...
const isFinished = game.metadata.winner !== ZERO_ADDRESS;
const isDraw = isFinished && game.metadata.winner === TIE_ADDRESS;
```

This is not waiting on redeploy — it's a bug against the **currently deployed** contract. Per `pre-audit.md`'s L-04 write-up, a draw has always set `winner = address(0)` (that's existing, already-live behavior; the fix only *adds* a new `ended` field to disambiguate it, it doesn't change what a draw already does). `TIE_ADDRESS` (`0x...01`) is never actually set by any version of the contract, old or new — it looks like a sentinel that was assumed to exist but never was.

**Practical effect, today:** a game that ends in a draw has `winner === ZERO_ADDRESS`, so `isFinished` evaluates `false`. The game sorts alongside genuinely-in-progress games (`Games.tsx`'s comparator treats `winner === ZERO_ADDRESS` as "still active") and never renders as a Draw. **Drawn games are permanently misclassified as in-progress in the games list, right now, in production.**

**Fix:** two parts.
1. **Now:** `TIE_ADDRESS` can be removed as dead code — nothing on-chain ever sets it, so `isDraw` is already unreachable via that path. This alone doesn't fix the misclassification (there's still no way to tell "in progress" from "drew" using only `winner`), but it removes code implying a distinction that doesn't exist.
2. **After redeploy:** once `GameMetadata.ended` exists in the ABI, add it to `GameMetadata`/`GameDataView` (`app/types/types.ts:219-229`, and its exact duplicate at `446-456` — worth deduping while touching this type regardless), and switch `isFinished` to `game.metadata.ended` and `isDraw` to `ended && winner === ZERO_ADDRESS`. That's the only way to correctly distinguish "still playing" from "ended in a draw."

### F — Lobbies exact-fee tightening — **[Low risk, confirm after redeploy]**

**Files:** `app/hooks/useLobbies.ts:65-116`

The contract's fee check changes from "at least" to "exactly" (overpaying now reverts instead of silently keeping the excess) — this isn't deployed yet either, so no current bug. Already low-risk regardless: `createLobby`'s `value` is computed with no buffer (`needsPayment ? additionalLobbyFee : 0n`), and `joinLobby` sends no `value` at all. The one thing worth confirming once redeployed (not before, since it can't be tested against a contract that doesn't have the new check yet): that `needsPayment`'s dependency on `activeLobbiesCount` can't go stale in a way that causes a false-positive "payment needed" — under the old "at least" check a stale false-positive silently overpaid and succeeded; under the new "exactly" check it will revert.
